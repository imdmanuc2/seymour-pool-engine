# REST API

**Document:** 11-REST-API.md

**Version:** 1.0 (Development)

---

# Purpose

The Seymour Pool Engine exposes a REST API that provides operational visibility into the mining platform.

The API is intended for:

- Nexus Command Center
- Administrative tools
- Monitoring systems
- Automation
- Future mobile applications
- Third-party integrations

The API is read-focused in Version 1.0, providing visibility into mining activity while operational control continues to be performed through the Stratum Engine and administrative workflows.

---

# API Architecture

```
Applications

        │

HTTP / JSON

        │

REST API

        │

Services

        │

Repositories

        │

PostgreSQL
```

Every endpoint ultimately retrieves data from the Seymour database.

---

# Base URL

Example

```
http://server:8561/api/v1/
```

Development example

```
http://127.0.0.1:8561/api/v1/
```

---

# API Versioning

Version 1 APIs use:

```
/api/v1/
```

Future releases may introduce:

```
/api/v2/
```

while maintaining backward compatibility where practical.

---

# Response Format

Responses use JSON.

Example:

```json
{
    "status": "online"
}
```

---

# Health Endpoints

Used by monitoring systems.

Example

```
GET

/api/v1/health
```

Returns:

- Engine status
- Database status
- Bitcoin Core status
- Overall health

---

# Statistics API

Provides mining statistics generated by the Native Statistics engine.

### Overview

```
GET

/api/v1/statistics/overview
```

Returns:

- Pool hashrate
- Active workers
- Accepted shares
- Rejected shares
- Efficiency
- Last share

---

### Worker Statistics

```
GET

/api/v1/statistics/workers
```

Returns:

- Worker list
- Current hashrate
- Difficulty
- Last activity
- Online status

---

### Worker Detail

```
GET

/api/v1/statistics/workers/{worker}
```

Returns statistics for an individual worker.

---

### Engine Statistics

```
GET

/api/v1/statistics/engine
```

Provides engine-level metrics including:

- Share processing
- Submission rate
- Engine performance

---

# Share API

Share-related endpoints expose mining activity.

Examples include:

- Recent submissions
- Accepted shares
- Rejected shares
- Historical statistics

These endpoints are intended for dashboards and troubleshooting.

---

# Session API

Session endpoints expose active mining connections.

Information includes:

- Connected workers
- Session duration
- Current difficulty
- Connection state

---

# Job API

Job endpoints provide visibility into mining work.

Information includes:

- Active jobs
- Job history
- Block heights
- Previous block hashes
- Template timestamps

---

# Difficulty API

Provides Variable Difficulty information.

Includes:

- Current worker difficulty
- Historical adjustments
- Retarget history

---

# Future Administrative APIs

Future versions may introduce authenticated administrative operations such as:

- Disconnect worker
- Pause mining
- Resume mining
- Reload templates
- Force statistics refresh
- Configuration management

These capabilities are intentionally outside the Version 1.0 scope.

---

# HTTP Status Codes

Typical responses include:

```
200 OK

400 Bad Request

401 Unauthorized

403 Forbidden

404 Not Found

409 Conflict

500 Internal Server Error
```

---

# Error Responses

Example:

```json
{
    "error": {
        "code": "worker_not_found",
        "message": "Worker does not exist."
    }
}
```

Errors are designed to be both human-readable and machine-readable.

---

# Pagination

Large result sets may support pagination.

Typical parameters include:

```
limit

offset
```

Future releases may also support cursor-based pagination.

---

# Filtering

Many endpoints support filtering.

Examples include:

- Worker
- Pool
- Time window
- Online status

---

# Time Windows

Statistics commonly support:

```
1m

5m

15m

1h

6h

24h
```

Additional windows may be added in future releases.

---

# Performance

The API is designed for:

- Low latency
- High concurrency
- Efficient database queries
- Native statistics caching

Expensive calculations are avoided whenever possible.

---

# Authentication

Version 1.0 assumes deployment within trusted infrastructure.

Future versions may support:

- API keys
- OAuth
- JWT
- Service accounts

Authentication requirements will evolve alongside remote administration features.

---

# Nexus Command Center Integration

Nexus Command Center consumes the REST API to display:

- Pool health
- Worker status
- Hashrate
- Share activity
- Native statistics
- Operational dashboards
- Infrastructure topology
- CMDB synchronization

The REST API forms the primary integration point between Seymour Pool Engine and the wider Seymour Platform.

---

# Stability

The REST API is intended to remain stable throughout the Version 1.x release cycle.

Breaking API changes should only occur with a new major version.

---

# Relationship to Other Components

The REST API exposes information from:

- Stratum Engine
- Native Statistics
- PostgreSQL
- Variable Difficulty
- Share Validation
- Job Engine

It serves as the primary external interface for applications interacting with Seymour.
